## Source authority and capacity

Visitor order input contains only an idempotency key, occurrence ID, quantity1–10 and expected published tour/occurrence versions. The server derives the scoped parent tour, published content, source hash/revisions/versions, title, capacity, unit price, total and `ILS`. Extra price/currency/merchant/URL/tour fields fail. Missing, withdrawn or cross-scope records, stale versions, zero price, unknown start/capacity and past occurrences fail closed. Current source occurrences retain their unknown booking facts.

A quote is immutable. Checkout rechecks it and atomically claims `creating` only while both source revisions/versions still match. The same D1 transaction checks the sum of reserved quantities for that scoped occurrence against its authoritative capacity. `creating`, `checkout_ready`, `uncertain` and `paid_verified` each retain exactly one order quantity. Competing orders cannot exceed capacity. Source capacity reduction does not erase existing reservations; it blocks additional claims. Time/checkout expiry never releases an uncertain provider hold. No source record or content history is changed.

Orders, unique transaction claims and one private `payment_verified` effect use scope-prefixed keys in existing `cms_settings`, with no migration or new queue. Confirmation and its effect commit atomically; one transaction cannot confirm two orders. Paid replay and acknowledgment updates do not insert another effect or reserve additional capacity. No fulfillment or notification authority is granted.

## One attempt, privacy and HTTP boundary

The compare-and-swap `prepared → creating` claim precedes the one provider create request. A timeout, crash or malformed response leaves `creating`/`uncertain` for reconciliation; it cannot automatically create another process. This is local attempt control, not a claim that Grow create has an idempotency-key parameter. Matching idempotent replay returns the existing result; changed payload/buyer/config conflicts.

Both routes enforce exact deployment-owned origin/path, no queries, isolated D1 and fixed `derech/derech-main` scope. Order JSON is capped at8KiB with a5second body deadline; callback forms are capped at16KiB with the same deadline. The order route requires exact Origin, `Sec-Fetch-Site:same-origin`, `X-Payment-Request:1`, JSON content type and acceptance of the server-pinned terms hash. No CORS permission is added. Callback authentication uses private process binding and accepted provider readback, not browser CSRF or invented signature headers.

Rate limits use only edge-owned `CF-Connecting-IP`, purpose-separated HMAC fingerprints and bounded expiry cleanup in private settings. Raw IP is never saved. Order ingress permits15requests/IP/minute and100/site/minute; new orders additionally permit5/IP/10minutes and100/site/hour. Existing idempotent replay does not spend new-order quota. Callback ingress permits60/IP/minute and600/site/minute. Missing edge identity or rate secret fails closed. Responses are no-store/noindex; errors expose fixed codes only.

No raw buyer/card/callback body is persisted. Buyer binding uses a purpose-separated HMAC under `PAYMENT_RATE_SECRET`, rather than an unkeyed PII digest. Private orders retain minimal process credentials and hashed transaction evidence. Existing encrypted backups include these scoped settings; never restore older payment state over newer provider activity. Public responses exclude merchant credentials, process ID/token, transaction token, quote internals and buyer fingerprints. Only documented wallet `authCode`, expiry, amount/currency, state and confirmation may be returned. The callback route returns only `{accepted:true}` after acknowledgment. [Provider response privacy](https://developers.grow.business/reference/growin-wallet-sdk-response).

## Read-only receipt pages

`/payment/success/` and `/payment/cancel/` are branded RTL server pages. Provider return URLs include only `?order=<opaque64hexID>`. A browser redirect, `response=success` or other query assertion never confirms payment. The renderer reads the scoped deployment row and saved order only; it has no provider transport, counters, mutations, cancellation/refund or capacity-release action. Confirmed UI requires saved `paid_verified`, confirmed acknowledgment and matching saved proof fields. Otherwise it honestly shows pending/unverified/unavailable. Cancel explains that leaving the payment page does not cancel or refund a charge, including when the saved payment was actually confirmed.

The pages require the same accepted review/production configuration and exact production profile. They default503 when disabled. Queries are bounded to512characters and allow only one opaque order ID plus non-authoritative provider response/cField1; unknown, duplicate, sensitive or mismatched fields fail. Missing orders disclose no buyer, amount or private order data. HTML contains no scripts, iframe, polling or automatic navigation, and returns private/no-store/noindex/noarchive/no-referrer with a strict CSP. Home and the existing WhatsApp link work only on manual click and carry no order data or referrer.

## Callback verification and acknowledgment

The documented callback is form data; URL-encoded and multipart are supported, while files, duplicate/unknown keys and JSON fail. No Grow HMAC scheme is invented. A paid single credit-card callback must bind the opaque order ID, saved process ID/token and exact amount before any provider inquiry. Under a separately Grow-approved merchant policy, `getTransactionInfo` must independently match process/transaction IDs and tokens, confirmation, paid status, payment count and amount. The official response has no currency field: currency is explicitly `verified-merchant-config`, tied to accepted `currencyEvidenceHash` and the immutable server quote. A contradictory returned currency fails. [Callback](https://developers.grow.business/reference/server-response), [inquiry parameters](https://developers.grow.business/reference/get-transaction-info), [inquiry response](https://developers.grow.business/reference/response-get-transaction-info).

Grow recommends inquiries for exceptional cases rather than every ordinary transaction. `callbackReadbackApproved` therefore requires merchant/provider acceptance of this security policy. It is not silently inferred from the general documentation. [Inquiry guidance](https://developers.grow.business/reference/transaction-inquiry-overview).

Acknowledgment is implemented using the official `approveTransaction` endpoint, its published form parameters and the documented success body: status1, empty err/data/message. Its states are pending/sending/confirmed/contract_blocked. A durable sending claim prevents concurrent acknowledgment; an expired sending lease or failed acknowledgment can retry from a genuine matching callback without creating/reverifying payment or another effect. No callback PII is retained for a new background sender. HTTP200 is returned only after actual matching acknowledgment success. [Acknowledgment request](https://developers.grow.business/reference/approve-transaction-1), [acknowledgment response](https://developers.grow.business/reference/copy-of-response).

The official acknowledgment request labels `paymentLinkProcessId` and `paymentLinkProcessToken` required, although the regular callback example omits them. The implemented full documented contract forwards actual callback values only. Missing fields produce `contract_blocked`; it does not invent IDs, defaults, card/customer fields or a guessed reduced request. Actual merchant acceptance must resolve this exact schema ambiguity. Grow states acknowledgment does not perform or cancel the charge, so verified payment remains recorded even when acknowledgment is pending. [Acknowledgment semantics](https://developers.grow.business/reference/approve-transaction).

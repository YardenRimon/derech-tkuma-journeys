# Automatic review deployment contract — 20 October 2026

This preparation targets only the existing isolated Cloudflare review Worker, D1 and media bucket. Source preparation changes no domain, Access policy, application data, outbound integration or provider plan. It is not proof that a workflow is installed, enabled or accepted live.

## Trigger, source and privilege boundary

`github-workflows/site-cloudflare.yml` retains manual dispatch from `main` and `production-foundation-20261019`. The prepared primary automatic path is now a reusable `workflow_call`: **Shared CMS checks** calls it in the same run through `deploy-review`, which `needs: verify`. Only a successful `verify` after a **push** to one of those exact branches in `YardenRimon/derech-tkuma-journeys` is eligible. Pull-request runs, forks, failed/skipped verification, another workflow path and other branches are rejected. No CI artifacts are downloaded or executed.

The same-run path requires new repository-level variable `DERECH_CF_VERIFIED_JOB_DEPLOY_ENABLED=true`. It defaults disabled when absent. The existing cross-run `workflow_run` path remains available as a separately gated legacy route; keep its old repository flag `DERECH_CF_AUTO_DEPLOY_ENABLED=false` to avoid duplicate deployments. An environment-level variable cannot enable `jobs.if`; remove obsolete environment-level copies to avoid confusing operators. This source preparation changes neither flag.

The reusable caller passes `needs.verify.result` as a required string input, but that input is not sufficient proof. The callee independently reads its actual `GITHUB_RUN_ID` and current `GITHUB_RUN_ATTEMPT` through read-only GitHub APIs. The run must be the exact same-repository push, source SHA/branch and `Shared CMS checks` workflow path. Its overall status may still be `in_progress` with a null conclusion because deployment is part of that run. The attempt-specific jobs endpoint must contain exactly one job named `verify`, completed successfully for the same run ID and head SHA. Wrong attempts, missing/duplicate/failed/skipped/pending verify jobs, mismatched SHA and oversized/incomplete job lists fail closed. The job schema need not contain `run_attempt`: the endpoint and run record bind the attempt; an optional job-level attempt must match if present. See [GitHub jobs for a workflow run attempt](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt).

The caller uses `./.github/workflows/site-cloudflare.yml`, so the callee comes from the same source commit as the caller; no default-branch workflow update, protected-main bypass or application merge is required. It passes no inherited secrets. The called job owns the existing protected environment and its existing environment secret. Enabled push runs disable caller-level cancellation on a newer push, so GitHub cannot interrupt their active reusable deployment through the outer CI concurrency group. Pull requests keep cancellation enabled; the callee retains the global non-cancelling review lock. [GitHub reusable workflow source identity](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows#calling-a-reusable-workflow)

The legacy [`workflow_run` event](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run) executes privileged follow-up workflows from the default branch. If separately enabled, it still requires successful completed push CI, checks out its exact `head_sha` and rereads that run. The new same-run path instead uses the caller's exact `GITHUB_SHA`. Both paths carry `WORKERS_CI_COMMIT_SHA` through build, artifact validation and live verification and reject a stale current branch head.

`cloudflare-cd-policy.mjs` rejects a checkout mismatch or missing application files. The current workflow-only `main` skeleton cannot deploy an application. This does not merge PR1 or otherwise authorize an application merge. The selected source must contain the policy and its focused test as well as the application. Run metadata and branch head are checked before the build and immediately before schema/application mutation. A source superseded while queued fails closed. The unavoidable small interval between GitHub head verification and provider mutation is bounded by adjacent steps; serialized, non-cancelling deployments and another guard before code upload prevent a stale queued run from silently replacing a newer selected head.

Actions remain pinned; permissions are `contents:read` and `actions:read`. The existing protected environment `derech-cloudflare-review`, private Cloudflare token, pinned media hash, full build/tests, resource/scope validators, noindex/source HTTP checks and concurrency lock are preserved. Configuration and provider secrets remain separate. The workflow does not turn on provider observability or change any secret scope.

## Installation and acceptance, performed by root

1. Set the old repository `DERECH_CF_AUTO_DEPLOY_ENABLED` flag `false`; keep the new verified-job flag `false` until manual/live acceptance. Complete or resolve an already-running manual deployment before pushing the new automation source. Neither setting nor active run is changed by these files.
2. Install both workflow templates as `.github/workflows/site-ci.yml` and `.github/workflows/site-cloudflare.yml` **on the application foundation branch only**, together with the policy/test/contract files. Normal CI and the deploy workflow both run the focused policy test. Do not modify or bypass protected `main`, merge application PR1 or change branch protection to enable this route. The CI workflow must retain its exact name/path and the `verify` job key/name; renames require a reviewed policy update.
3. Confirm the protected environment admits only the two approved branches and retains required owner approval where configured. Verify its scoped provider secret and existing reviewed config/media variables. Do not copy provider secrets into repository variables or the preceding CI workflow.
4. Complete manual review deployment and live owner/admin UI, Access, noindex, source/media/data and rollback readiness acceptance. Root then explicitly sets only **repository** `DERECH_CF_VERIFIED_JOB_DEPLOY_ENABLED=true`; the old flag stays `false`.
5. Observe a fresh trusted push run with successful `verify` followed by `deploy-review / deploy` in that same run: run/attempt, tested head SHA, checkout SHA, build/source header and live HTTP acceptance must agree. The same-run route remains prepared until root records this actual proof. A successful provider upload alone is insufficient. Record any failed post-upload verification as a failed deployment acceptance; code might already be live.
6. Pull-request CI must leave deployment skipped. Changing both repository flags to `false` stops future automatic jobs; it does not cancel an active job. Resolve that existing run explicitly before manual rollback. A rerun that lacks a successful `verify` in its current attempt is deliberately rejected; run complete CI again or use the separately protected manual route.

Environment `vars` are available only after the runner declares the environment; unset variables evaluate to an empty string. This is why the scheduling guard uses a repository variable. [GitHub vars context](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#vars-context)

## Manual code rollback plan

Before each accepted release, retain the provider's prior verified Worker version ID, corresponding source SHA, private reviewed resource config, database migration level and runtime-binding/secret compatibility evidence. Ordinary migrations must be additive and remain compatible with that retained version. A destructive migration or incompatible data transition needs its own reviewed migration and fresh recovery plan; this workflow does not classify SQL safety automatically.

On a failed release, first disable automatic review deployment and resolve any active run under the same deployment lock. Inspect the current provider deployment and select the **explicit previously verified version**, not an inferred “previous” version. Using the existing private reviewed config and scoped provider credential, root can inspect the installed CLI's `wrangler deployments list`/`wrangler versions view` and run:

```sh
npx wrangler rollback "$VERIFIED_PREVIOUS_VERSION_ID" --name derech-tkuma-review --config "$REVIEW_CONFIG" --message "Reviewed code rollback"
```

This is a prepared operator command, not an executed rollback. Keep its interactive confirmation. Verify retained version/source/noindex, all public pages, owner login, data compatibility and monitor health after it. Check current secret/binding compatibility first; a provider can reject a rollback when secret versions changed. Preserve the failed version and diagnostic evidence.

Never automatically roll back, reset or overwrite D1/R2. A code rollback retains current data/history and additive migrations. If data recovery is necessary, restore a fresh encrypted backup into a separate isolated database/bucket and compare it before an explicitly authorized switch. Final-domain/DNS migration remains a separate acceptance phase.
